# Программа: автотесты UI (Playwright) и API на Python, уровень Senior

**Формат:** 14 недель, 8–10 часов в неделю. Каждый модуль: теория → практика на стенде → артефакт в портфолио.

**Стенд:** свой сервис на FastAPI «мини-биржа» с веб-интерфейсом (`/app/`): баланс, ордера, частичное исполнение, WebSocket-стакан, вебхуки, JWT и HMAC-подпись. В него специально закладываются баги, которые потом ловятся тестами.


**Порядок (с 2026-10-07):** курс начат заново. Сначала часть UI — Playwright от основ до Senior (модули U1–U8),
затем фокус смещается на API (модули 1–12 ниже), в конце — связка UI + API.

---

## Часть UI. Playwright

### Модуль U1. Основы
- [ ] Установка, pytest-playwright, фикстуры `page`/`context`/`browser`, headed и headless, `--slowmo`
- [ ] Первый тест: открыть страницу, заполнить форму входа, проверить кабинет
- [ ] Локаторы: `get_by_role`, `get_by_label`, `get_by_text`, `get_by_test_id`; почему не XPath
- [ ] Действия: `click`, `fill`, `select_option`, `check`; авто-ожидание (actionability)
- [ ] Проверки `expect(...)`: `to_be_visible`, `to_have_text`, `to_have_count`; почему не `assert` и не `sleep`

### Модуль U2. Устойчивые тесты
- [ ] Цепочки и фильтры локаторов: `locator().filter(has_text=...)`, `nth`, строки таблиц
- [ ] Ожидания асинхронного UI: автообновление, тосты, кнопка disabled, сетевые ответы (`expect_response`)
- [ ] Почему тесты флейкают и как это лечить без `wait_for_timeout`
- [ ] Codegen и Inspector: записать сценарий и переписать его нормально

### Модуль U3. Page Object
- [ ] Page Object и компоненты (таблица ордеров, форма, тост) — что выносить, что нет
- [ ] Фикстуры страниц; базовый URL и конфиг окружений
- [ ] **Артефакт:** каркас UI-фреймворка

### Модуль U4. Данные и состояние
- [ ] Подготовка данных через API, проверка в UI (быстрее и надёжнее, чем кликать)
- [ ] `storage_state`: логин один раз, переиспользование сессии; несколько пользователей в одном тесте
- [ ] Изоляция: новый `context` на тест, cleanup

### Модуль U5. Сеть
- [ ] Перехват и мок ответов (`page.route`): ошибки сервера, пустые списки, медленный ответ
- [ ] Проверка запросов, которые отправляет фронт; HAR
- [ ] **Сценарий:** API отдал 500 при создании ордера — UI показывает понятную ошибку

### Модуль U6. Отладка и отчёты
- [ ] Trace Viewer, скриншоты и видео на падении, Allure
- [ ] Разбор флейков, ретраи `pytest-rerunfailures` — когда можно, когда нельзя

### Модуль U7. Масштаб
- [ ] Параллельный запуск (xdist), кросс-браузерность, мобильная эмуляция
- [ ] Визуальные проверки (скриншот-сравнение), базовая доступность
- [ ] Запуск в Docker и CI

### Модуль U8. Senior
- [ ] Стратегия UI vs API: пирамида тестов, что автоматизировать в UI, а что нет
- [ ] Гибридные тесты: шаг в API → проверка в UI → проверка в БД
- [ ] Ревью UI-тестов, типичные ошибки, вопросы собеседований

## Модуль 0. Git и GitHub (нед. 1, параллельно с модулем 1)

- [ ] Базовый цикл: `status`, `add`, `commit`, `push`, `pull`; что такое коммит, ветка и `HEAD`
- [ ] `.gitignore`: что никогда не попадает в репозиторий (секреты, `.venv`, `allure-results`)
- [ ] Сообщения коммитов по Conventional Commits: `feat:`, `fix:`, `test:`, `chore:`
- [ ] GitHub Flow: `main` всегда рабочий, каждая задача — отдельная ветка
- [ ] Pull Request: описание, самопроверка диффа, ревью, squash merge, удаление ветки
- [ ] Конфликты: merge и rebase, разрешение конфликта руками
- [ ] `gh` CLI: создать PR, посмотреть ревью, проверить статус CI из терминала
- [ ] Issues и labels: каждый найденный баг стенда — issue с шагами воспроизведения и ссылкой на тест
- [ ] **Сценарий:** каждое задание курса сдаётся через Pull Request, ревью идёт комментариями в PR

## Модуль 1. Архитектура фреймворка (нед. 1–2)

- [ ] httpx (sync и async) вместо requests, своя обёртка клиента
- [ ] Слои: client, service/steps, models, tests, fixtures
- [ ] Конфиги и окружения через pydantic-settings
- [ ] Логирование запросов и ответов в Allure, маскирование секретов
- [ ] Retry с tenacity, но только там, где это оправдано
- [ ] **Сценарий:** один и тот же набор тестов гоняется на local, docker и stage без изменений кода
- [ ] **Артефакт:** каркас стенда + каркас фреймворка

## Модуль 2. Контракты и схемы (нед. 2–3)

- [ ] Строгая валидация ответов через Pydantic v2 (`extra="forbid"`, точные типы)
- [ ] Генерация клиента и моделей из OpenAPI
- [ ] Schemathesis: property-based фаззинг прямо по спецификации
- [ ] Consumer-driven contract testing с Pact
- [ ] **Сценарий:** ловим breaking change (поле стало nullable, поменялся enum) до того, как это дошло до фронта

## Модуль 3. Данные и изоляция (нед. 3–4)

- [ ] Фабрики через polyfactory или factory_boy, Faker
- [ ] Scope фикстур, гарантированный cleanup, финализаторы
- [ ] Параллельный запуск на pytest-xdist без конфликтов данных
- [ ] Проверка побочных эффектов напрямую в БД (SQLAlchemy)
- [ ] testcontainers-python: Postgres, Redis, Kafka поднимаются из теста

## Модуль 4. Сложная бизнес-логика (нед. 4–6) — ядро программы

- [ ] Stateful testing: `hypothesis.stateful.RuleBasedStateMachine` — случайные последовательности (депозит, ордер, отмена, вывод) с инвариантами, например «баланс никогда не уходит в минус»
- [ ] Конкурентность и гонки: `asyncio.gather` на 50 одновременных ордеров с одного баланса (double spend), отмена ордера одновременно с исполнением
- [ ] Идемпотентность: повтор запроса с Idempotency-Key, повтор после таймаута
- [ ] Eventual consistency: polling с таймаутом вместо `sleep`
- [ ] Деньги: Decimal, округление, минимальный шаг лота, частичное исполнение
- [ ] Пагинация: курсорная пагинация, пока данные меняются (дубли и пропуски)
- [ ] Время: таймзоны, границы суток, истечение ордеров

## Модуль 5. Не-REST протоколы (нед. 6–7)

- [ ] WebSocket: подписка, порядок сообщений, пропуски sequence в стакане, реконнект
- [ ] Вебхуки: локальный приёмник на pytest-httpserver, проверка подписи и повторных доставок
- [ ] GraphQL: ограничения по глубине и сложности, N+1
- [ ] gRPC: тесты по proto, коды ошибок
- [ ] Kafka: проверка, что событие опубликовано с правильной схемой

## Модуль 6. Моки и отказоустойчивость (нед. 7–8)

- [ ] respx для httpx, WireMock для внешних сервисов
- [ ] Toxiproxy: задержки, обрывы соединения, медленный ответ внешнего провайдера цен
- [ ] **Сценарий:** внешний price feed отвечает 5 секунд или отдаёт 500 — система не исполняет ордер по устаревшей цене

## Модуль 7. Безопасность API (нед. 8–9)

- [ ] OWASP API Security Top 10 (2023): BOLA/IDOR, BFLA, mass assignment, отсутствие rate limit
- [ ] JWT: `alg: none`, подмена подписи, истёкший токен, ротация refresh-токена
- [ ] HMAC-подпись с timestamp и recvWindow (как на Binance): replay-атака, сдвиг часов
- [ ] **Сценарий:** пользователь A отменяет ордер пользователя B, подставив чужой id

## Модуль 8. Производительность в функциональных тестах (нед. 9–10)

- [ ] Лёгкие проверки времени ответа в функциональных тестах (бюджеты, без флаки)
- [ ] Базовые понятия: latency vs throughput, перцентили p50/p95/p99, SLA/SLO
- [ ] Первый Locust-скрипт как smoke-проверка (подробно — в модулях 11–12)

## Модуль 9. CI/CD и надёжность прогонов (нед. 10–11)

- [ ] GitHub Actions: матрица окружений, шардирование, кэш зависимостей
- [ ] Защита `main`: обязательные проверки CI и ревью перед merge, шаблон PR, CODEOWNERS
- [ ] docker-compose окружение для CI
- [ ] Flaky-тесты: поиск причин, карантин, метрики (не лечим через rerun)
- [ ] Allure с историей и трендами, уведомления
- [ ] Корреляционный id и OpenTelemetry-трейсы для разбора падений

## Модуль 10. Senior-навыки (нед. 11–12)

- [ ] Стратегия тестирования API: risk-based подход, что автоматизировать, а что нет
- [ ] Code review тестов, гайдлайны для команды
- [ ] ADR по архитектурным решениям фреймворка
- [ ] Метрики качества, понятные менеджменту

## Модуль 11. Нагрузочное тестирование с Locust: сценарии (нед. 12–13)

- [ ] Архитектура Locust: `User`, `HttpUser` vs `FastHttpUser`, gevent, почему нельзя блокировать
- [ ] Задачи: `@task` с весами, `TaskSet`, `SequentialTaskSet`, `wait_time` (between, constant_throughput, constant_pacing)
- [ ] `on_start` / `on_stop`: логин и JWT, обновление токена во время теста
- [ ] HMAC-подпись запросов внутри Locust (переиспользуем код из фреймворка, а не копируем)
- [ ] Тестовые данные: пул заранее созданных пользователей, без конфликтов между виртуальными юзерами
- [ ] `catch_response`: бизнес-валидация ответа (200 с ошибкой в теле = fail)
- [ ] Группировка URL с id через `name=` (иначе статистика разваливается на тысячи строк)
- [ ] Кастомный User для WebSocket-стакана: ручная отправка метрик через `events.request.fire`
- [ ] Запуск: web UI, headless, `locust.conf`, отчёты CSV и HTML
- [ ] **Сценарий:** реалистичный профиль трейдера — 70% чтение стакана, 20% выставление ордера, 10% отмена; проверяем, что под нагрузкой не нарушаются инварианты баланса
- [ ] **Артефакт:** `load/` в репозитории со сценариями и README по запуску

## Модуль 12. Нагрузочное тестирование с Locust: профили, SLA и анализ (нед. 13–14)

- [ ] Профили нагрузки через `LoadTestShape`: step (ступени), spike (всплеск), stress (до отказа), soak (несколько часов)
- [ ] SLA-проверки в коде: хуки `events.quitting` / `test_stop`, пороги p95/p99 и error rate → ненулевой exit code
- [ ] Распределённый запуск: master + workers в docker-compose
- [ ] Метрики: экспорт в Prometheus/Grafana (locust-plugins / exporter), корреляция с метриками сервиса (CPU, пул соединений БД, event loop lag)
- [ ] Поиск узкого места: py-spy / профилирование стенда, N+1 в списке ордеров, lock contention на балансе
- [ ] Soak-тест: утечки памяти (например, неотписанные WebSocket-подписки) и деградация p99 со временем
- [ ] Capacity-тест: находим точку насыщения и формулируем «сколько RPS выдерживает сервис при p95 < X мс»
- [ ] Нагрузка в CI: nightly-прогон, сравнение с baseline, алерт при регрессии производительности
- [ ] **Сценарий:** в стенд заложены perf-баги (N+1, глобальная блокировка, утечка в WS) — каждый находим нагрузкой и доказываем графиком до/после фикса
- [ ] **Артефакт:** performance-отчёт в портфолио: профиль, графики, SLA, найденные узкие места, выводы по capacity
