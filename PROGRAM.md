# Программа: автотесты UI (Playwright) и API на Python, уровень Senior

**Формат:** 14 недель, 8–10 часов в неделю. Каждый модуль: теория → практика на стенде → артефакт в портфолио.

**Стенд:** свой сервис на FastAPI «мини-биржа» с веб-интерфейсом (`/app/`): баланс, ордера, частичное исполнение, WebSocket-стакан, вебхуки, JWT и HMAC-подпись. В него специально закладываются баги, которые потом ловятся тестами.


**Порядок (с 2026-10-07):** курс начат заново. Параллельно идёт фундамент (F1–F4: Python, тест-дизайн, SQL, Linux/Docker/K8s). Сначала часть UI — Playwright от основ до Senior (модули U1–U10),
затем фокус смещается на API (модули 1–12 ниже), в конце — связка UI + API.

## Часть UI. Playwright (10 модулей)

Все уроки одним документом: `practice/UI_COURSE.md` (собирается `uv run python practice/build_ui_course.py`). Лаборатория для U3/U6/U10: `/app/lab.html`.

Каждый модуль закрывает типовые вопросы собеседований — они отмечены **Собес:**.

### Модуль U1. Основы и устройство Playwright
- [ ] Установка, pytest-playwright, фикстуры `page` / `context` / `browser`, `--headed`, `--slowmo`, `--browser`
- [ ] Первые тесты: страница входа, логин, кабинет; `goto`, `fill`, `click`, `select_option`, `check`
- [ ] Локаторы: `get_by_role`, `get_by_label`, `get_by_text`, `get_by_placeholder`, `get_by_test_id`; приоритет локаторов
- [ ] Проверки `expect(...)`: `to_be_visible`, `to_have_text`, `to_have_value`, `to_have_count`, `to_have_url`
- [ ] Как устроен Playwright: Python-клиент → driver (отдельный процесс) → браузер; одно постоянное соединение, события приходят сами
- [ ] Протоколы браузеров: CDP для Chromium, встроенные протоколы в собранных Firefox и WebKit; сравнение с W3C WebDriver (Selenium) и «внутри браузера» (Cypress)
- [ ] Модель Browser → BrowserContext → Page → Frame: что изолирует context (cookies, localStorage, кэш, разрешения), почему context дешёвый, а browser дорогой
- [ ] Как pytest-playwright раздаёт объекты: browser — один на прогон, context и page — новые на каждый тест; два пользователя = два context
- [ ] Как Playwright ждёт сам: ленивые локаторы (ищутся при каждом действии, нет stale element), actionability-проверки перед действием, повтор `expect`, strict mode
- [ ] sync и async API: синхронный — обёртка над асинхронным, когда какой
- [ ] pytest для UI: встроенные фикстуры pytest-playwright (`page`, `context`, `browser`, `browser_name`, `base_url`), `conftest.py`, `parametrize`, маркеры
- [ ] **Собес:** чем Playwright отличается от Selenium и Cypress (протокол, скорость, ожидания, вкладки, языки)
- [ ] **Собес:** какие локаторы выбираешь и почему не XPath / длинные CSS-цепочки
- [ ] **Собес:** что такое BrowserContext и зачем новый context на каждый тест

## Модуль 0. Git и GitHub (параллельно с модулем 1)

- [ ] Базовый цикл: `status`, `add`, `commit`, `push`, `pull`; что такое коммит, ветка и `HEAD`
- [ ] `.gitignore`: что никогда не попадает в репозиторий (секреты, `.venv`, `allure-results`)
- [ ] Сообщения коммитов по Conventional Commits: `feat:`, `fix:`, `test:`, `chore:`
- [ ] GitHub Flow: `main` всегда рабочий, каждая задача — отдельная ветка
- [ ] Pull Request: описание, самопроверка диффа, ревью, squash merge, удаление ветки
- [ ] Конфликты: merge и rebase, разрешение конфликта руками
- [ ] `gh` CLI: создать PR, посмотреть ревью, проверить статус CI из терминала
- [ ] Issues и labels: каждый найденный баг стенда — issue с шагами воспроизведения и ссылкой на тест
- [ ] **Сценарий:** каждое задание курса сдаётся через Pull Request, ревью идёт комментариями в PR

## Модуль 11. Нагрузочное тестирование с Locust: сценарии

- [ ] Архитектура Locust: `User`, `HttpUser` vs `FastHttpUser`, gevent, почему нельзя блокировать
- [ ] Обзор альтернатив: JMeter и k6 — чем отличаются от Locust, когда что выбирают
- [ ] Задачи: `@task` с весами, `TaskSet`, `SequentialTaskSet`, `wait_time` (between, constant_throughput, constant_pacing)
- [ ] `on_start` / `on_stop`: логин и JWT, обновление токена во время теста
- [ ] HMAC-подпись запросов внутри Locust (переиспользуем код из фреймворка, а не копируем)
- [ ] Тестовые данные: пул заранее созданных пользователей, без конфликтов между виртуальными юзерами
- [ ] `catch_response`: бизнес-валидация ответа (200 с ошибкой в теле = fail)
- [ ] Группировка URL с id через `name=` (иначе статистика разваливается на тысячи строк)
- [ ] Кастомный User для WebSocket-стакана: ручная отправка метрик через `events.request.fire`
- [ ] Запуск: web UI, headless, `locust.conf`, отчёты CSV и HTML
- [ ] **Сценарий:** реалистичный профиль трейдера — 70% чтение стакана, 20% выставление ордера, 10% отмена; проверяем, что под нагрузкой не нарушаются инварианты баланса
- [ ] **Артефакт:** `load/` в репозитории со сценариями и README по запуску

## Модуль 12. Нагрузочное тестирование с Locust: профили, SLA и анализ

- [ ] Профили нагрузки через `LoadTestShape`: step (ступени), spike (всплеск), stress (до отказа), soak (несколько часов)
- [ ] SLA-проверки в коде: хуки `events.quitting` / `test_stop`, пороги p95/p99 и error rate → ненулевой exit code
- [ ] Распределённый запуск: master + workers в docker-compose
- [ ] Метрики: экспорт в Prometheus/Grafana (locust-plugins / exporter), корреляция с метриками сервиса (CPU, пул соединений БД, event loop lag)
- [ ] Поиск узкого места: py-spy / профилирование стенда, N+1 в списке ордеров, lock contention на балансе
- [ ] Soak-тест: утечки памяти (например, неотписанные WebSocket-подписки) и деградация p99 со временем
- [ ] Capacity-тест: находим точку насыщения и формулируем «сколько RPS выдерживает сервис при p95 < X мс»
- [ ] Нагрузка в CI: nightly-прогон, сравнение с baseline, алерт при регрессии производительности
- [ ] **Сценарий:** в стенд заложены perf-баги (N+1, глобальная блокировка, утечка в WS) — каждый находим нагрузкой и доказываем графиком до/после фикса
- [ ] **Артефакт:** performance-отчёт в портфолио: профиль, графики, SLA, найденные узкие места, выводы по capacity
