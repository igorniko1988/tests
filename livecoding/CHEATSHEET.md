# Шпаргалка лайвкодинга API

Порядок ответа всегда один: **понять → вопросы → чек-лист → приоритет → код → итог.**
Первые 5 минут — только текст, ни строчки кода.

---

## 1. Уточняющие вопросы (выбери 3–5 подходящих)

**Параметры и данные**
- Что означает параметр? В каких единицах? (`commercial` — процент?)
- Обязательный ли параметр? Какое значение по умолчанию?
- Границы включительно? (от 18 до 120 — 120 разрешено?)
- Какие типы допустимы? Что с `1.5`, `"01"`, пустой строкой, очень большим числом?
- Регистр важен? (`active` / `Active`), пробелы обрезаются?

**Ответ**
- Может ли поле быть `null` или отсутствовать?
- Может ли список быть пустым? Есть ли лимит/пагинация?
- Порядок элементов гарантирован? По какому полю сортировка?
- Формат дат и денег (UTC? строка или число?)

**Ошибки**
- Какие коды ответа: 400 или 422? 404 или 403 на чужой объект?
- Формат тела ошибки? Есть ли код ошибки и описание?

**Доступ и окружение**
- Нужна ли авторизация? Разные роли видят разное? Можно ли видеть чужие данные?
- Есть ли тестовые данные или их нужно создавать? Стабильны ли они?
- Есть ли SLA по времени ответа, rate limit?

Если отвечают «решай сам» — **вслух зафиксируй допущение**: «Считаю, что граница включительно».

## 2. Чек-лист — категории сверху вниз

1. **Позитивные** — основной сценарий, ответ по схеме, значения соответствуют запросу.
2. **Граничные значения** — для диапазона `min..max`: `min-1, min, min+1, max-1, max, max+1`.
3. **Классы эквивалентности** — по одному значению из группы: внутри, ниже, выше,
   не тот тип (`"abc"`), дробное, пустое, не передан.
4. **Несуществующие объекты** — `404`: граница за последним id, заведомо большой id.
5. **Бизнес-логика** — то, ради чего эндпоинт существует (фильтр работает, сумма считается).
6. **Безопасность и доступ** — без токена (401), чужой объект (403/404), лишние данные в ответе.
7. **Нефункциональные** — неверный метод (405), время ответа, Content-Type, большие объёмы.

Техники называть по именам: **граничные значения**, **классы эквивалентности**,
для нескольких параметров — **попарное тестирование (pairwise)**,
для объектов со статусами — **переходы состояний**.

## 3. Приоритет (risk-based)

| Приоритет | Что | Почему |
|---|---|---|
| **P0** | основной сценарий: валидный запрос → 200 + схема + правильные данные | без него эндпоинт бесполезен |
| **P0** | деньги, безопасность, чужие данные | самые дорогие ошибки |
| **P1** | границы и валидация (400/404) | самые частые баги |
| **P2** | бизнес-нюансы, комбинации параметров | важны, но реже ломаются |
| **P3** | нефункциональные, редкие кейсы | проговорить, если нет времени писать |

Фраза для собеса: «Начну с P0 — основной сценарий. Потом границы и ошибки. Остальное проговорю».

## 4. Шаблон кода

```python
import pytest
import requests
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, StrictInt, StrictStr

BASE_URL = "http://localhost:8090/v1/..."


class Item(BaseModel):
    model_config = ConfigDict(extra="forbid")      # лишние поля запрещены

    id: StrictInt
    name: StrictStr = Field(min_length=1)         # не пустая строка
    price: float = Field(gt=0)                    # > 0
    status: Literal["active", "blocked"]          # одно из списка


def call(item_id):
    return requests.get(f"{BASE_URL}/{item_id}", timeout=10)   # всегда timeout


# P0
@pytest.mark.parametrize("item_id", [1, 2, 3])
def test_existing_item_is_returned(item_id):
    response = call(item_id)

    assert response.status_code == 200
    item = Item.model_validate(response.json())   # без assert
    assert item.id == item_id                      # работаем с моделью


# P1
@pytest.mark.parametrize(
    ("item_id", "status_code", "error"),
    [(0, 400, "bad_request"), ("abc", 400, "bad_request"), (999, 404, "not_found")],
)
def test_item_errors(item_id, status_code, error):
    response = call(item_id)

    assert response.status_code == status_code
    assert response.json() == {"error": error}     # тело целиком
```

**Модель — что куда:**
- тип строго: `StrictInt`, `StrictStr`, `StrictFloat`, `StrictBool`
- диапазон: `Field(ge=, le=, gt=, lt=)`; длина строки: `Field(min_length=, max_length=)`
- одно из списка: `Literal[...]`; email: `EmailStr`; дата с поясом: `AwareDatetime`
- может отсутствовать: `int | None = None`; вложенный объект: поле с типом другой модели
- список объектов: `list[Item]`

## 5. Частые ошибки (из разборов)

- Пустые вопросы/чек-лист — половина оценки потеряна.
- Ожидание подогнано под ответ сервера — ожидания только из документации.
- `random` для выбора, что проверять — проверяй все данные через `parametrize`.
- Проверка значения вместо типа (`in_stock is True`, а может быть `False`).
- `is not None` вместо «не пустая строка»; `float` без Strict принимает строку `"59.5"`.
- Смешаны 400 и 404: 400 — неправильный запрос, 404 — объекта нет.
- `assert Model.model_validate(...)` и потом снова `response.json()[...]`.
- Ошибку проверяют моделью успешного ответа.
- Нет `timeout=` в requests.
