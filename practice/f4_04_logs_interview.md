# F4. Урок 4 — логи и мониторинг; собес «тест упал на стенде»

Задания: `practice/f4_04_logs_interview_answers.md`.

## 1. Что такое хороший лог

Наш стенд пишет одну JSON-строку на запрос:

```json
{"level": "WARNING", "request_id": "demo-123", "method": "GET", "path": "/orders", "status": 401, "duration_ms": 9.6}
```

- **уровни**: DEBUG (подробности) → INFO (обычные события) → WARNING (странно, но работаем, у нас 4xx) →
  ERROR (сбой, у нас 5xx) → CRITICAL;
- **структурированный (JSON)** лог можно фильтровать по полю, а не только grep'ом по тексту;
- **request id** (он же correlation id / trace id) — уникальный id запроса. Его передают через все сервисы
  в заголовке (у нас `X-Request-ID`) и пишут в каждую строку лога. По нему собирается вся история одного запроса.

## 2. Request id из тестов

Лучшая практика: **тест сам генерирует request id** и отправляет в заголовке, а при падении печатает его.

```python
rid = str(uuid.uuid4())
response = session.post("/orders", json=..., headers={"X-Request-ID": rid})
# при падении: "request_id=... — ищи в логах"
```

Или сервис возвращает его в ответе (у нас — заголовок `X-Request-ID` в каждом ответе), а клиент
фреймворка прикладывает его к Allure-шагу. Тогда от упавшего теста до строки лога — одна копипаста.

## 3. Централизованные логи: ELK / Kibana, Loki / Grafana

Когда подов десятки, `docker logs` не годится. Логи всех сервисов собираются в одно хранилище:

- **ELK**: Elasticsearch (хранит) + Logstash/Fluentd (собирает) + **Kibana** (интерфейс поиска);
- **Loki + Grafana** — то же, легче.

Как читать в Kibana (Discover):
1. выбрать индекс/сервис и **временной диапазон** (время падения теста ± пара минут);
2. фильтр по полю: `request_id: "demo-123"` или `level: ERROR and service: exchange`;
3. открыть запись → смотреть stack trace, соседние записи того же request id в других сервисах.

В Grafana Loki — запросы LogQL: `{app="exchange"} |= "demo-123"` или `{app="exchange"} | json | status >= 500`.

## 4. Метрики и мониторинг (читать, не настраивать)

- **Prometheus** собирает числа (метрики), **Grafana** рисует графики.
- Что смотреть при падении тестов: **RPS**, **error rate** (доля 5xx), **latency p95/p99**,
  CPU/память подов, рестарты.
- **p95 = 300 мс** — 95% запросов быстрее 300 мс. Среднее прячет медленные хвосты, поэтому смотрят перцентили.
- **Трейсинг** (Jaeger, Tempo, OpenTelemetry) — путь одного запроса через все сервисы с временем каждого шага.

Если на графике в момент падения error rate подскочил у всех — проблема стенда, а не теста.

## 5. Собес: «Тест упал на стенде. Как найдёшь причину?»

Схема ответа (говори по шагам):

1. **Отчёт теста**: какой шаг, какая ошибка (assert / таймаут / 5xx / connection refused). Есть ли request id,
   ответ сервиса, для UI — скриншот, видео, trace.
2. **Воспроизводится?** Перезапуск одного теста. Падает всегда → баг или изменение. Иногда → flaky:
   смотрю историю в Allure/CI, параллельность, данные, тайминги.
3. **Стенд жив?** `/health`, статус подов (`kubectl get pods`: рестарты, CrashLoop), Grafana: error rate,
   был ли деплой в это время (новая версия?).
4. **Логи по request id** в Kibana/Loki или `kubectl logs ... | grep <id>` — какой сервис ответил ошибкой,
   stack trace. Если сервисов несколько — идём по цепочке.
5. **Данные**: проверка в БД — то ли сохранилось, нет ли «грязных» данных от других тестов.
6. **Вывод**: баг продукта → баг-репорт (curl, request id, лог); проблема теста → чиню тест;
   проблема окружения → к DevOps с фактами (под, время, событие).

Типичные причины: деплой во время прогона, общие данные между тестами, гонки, таймауты стенда,
протухший токен, изменённый контракт API, нехватка ресурсов стенда.
