## 1. Зачем QA лезть в базу

API ответил 201 — но записалось ли то, что нужно?

- **проверить результат**: после `POST /orders` в таблице `orders` есть строка с нужными полями, а в
  `balances` заблокированы деньги;
- **подготовить данные**, которые через API не создать (например, старый ордер, редкий статус);
- **найти причину бага**: «в UI баланс 0» — в базе 0 или фронт не так показал?
- **проверить консистентность**: сумма locked = сумма по открытым ордерам.

Правило: **основная проверка — через API** (так работает пользователь). БД — дополнительная, где API не
показывает нужное, или для подготовки. Тест, который проверяет только БД, ломается при каждой смене схемы.

## 2. Подключение из Python: psycopg 3

```python
import psycopg
from psycopg.rows import dict_row

DSN = "postgresql://exchange:exchange@localhost:5432/exchange"

with psycopg.connect(DSN, row_factory=dict_row) as conn:          # with закроет соединение
    row = conn.execute(
        "SELECT status, price FROM orders WHERE id = %s",          # %s — параметр
        (order_id,),                                               # значения отдельно, кортежем
    ).fetchone()                                                   # одна строка (dict) или None
    rows = conn.execute("SELECT * FROM orders LIMIT 5").fetchall() # список строк
```

### Никогда не склеивай SQL строкой

```python
conn.execute(f"SELECT * FROM users WHERE email = '{email}'")   # ❌ SQL-инъекция, ломается на кавычке
conn.execute("SELECT * FROM users WHERE email = %s", (email,)) # ✅ драйвер сам экранирует
```

### В тестах — фикстура

```python
@pytest.fixture(scope="session")
def db():
    with psycopg.connect(settings.db_dsn, row_factory=dict_row, autocommit=True) as conn:
        yield conn
```

DSN — из настроек окружения (как base_url), не хардкодом.

## 3. Транзакции

Транзакция — группа изменений, которая выполняется **целиком или никак**.

```sql
BEGIN;
UPDATE balances SET available = available - 100 WHERE user_id = 1 AND asset = 'USDT';
UPDATE balances SET available = available + 100 WHERE user_id = 2 AND asset = 'USDT';
COMMIT;      -- сохранить оба. ROLLBACK; — отменить оба
```

**ACID**:
- **A**tomicity — всё или ничего;
- **C**onsistency — после транзакции данные корректны (ограничения соблюдены);
- **I**solation — параллельные транзакции не видят «половину» друг друга;
- **D**urability — после COMMIT данные не пропадут даже при падении сервера.

В psycopg без `autocommit=True` каждая работа идёт в транзакции: изменения не видны другим, пока не `conn.commit()`.
Частый баг в тестах: «вставил данные через БД, а API их не видит» — забыл commit.

### Изоляция и гонки (обзор)

Уровни: Read Committed (по умолчанию в Postgres), Repeatable Read, Serializable.
Две транзакции одновременно читают баланс 100 и обе списывают — **lost update** (та же гонка, что в asyncio-уроке).
Защита в коде: `SELECT ... FOR UPDATE` (заблокировать строку до конца транзакции) или атомарный
`UPDATE ... SET available = available - 100 WHERE available >= 100`.
Тестируется это **параллельными запросами к API** и проверкой итогового баланса.

## 4. Индексы

Индекс — как оглавление в книге: найти строку, не перебирая всю таблицу.

```sql
CREATE INDEX ix_orders_user_id ON orders (user_id);
EXPLAIN SELECT * FROM orders WHERE user_id = '...';    -- план: Index Scan (по индексу) или Seq Scan (перебор)
```

- ускоряют `WHERE`, `JOIN`, `ORDER BY` по этим колонкам;
- **замедляют** INSERT/UPDATE (индекс тоже надо обновить) и занимают место;
- `PRIMARY KEY` и `UNIQUE` создают индекс автоматически;
- UNIQUE-индекс — ещё и **ограничение**: наша таблица `users.email UNIQUE` — поэтому повторная регистрация → 409.

QA-уровень: понимать, почему запрос медленный (`EXPLAIN`), и что уникальность обеспечивает база.

## 5. Изоляция тестов и данные

- каждый тест создаёт **своего** пользователя (уникальный email) — тесты не мешают друг другу и идут параллельно;
- не удаляй «всё» после теста на общем стенде — удаляй своё или не удаляй вовсе (уникальные данные);
- `TRUNCATE` / пересоздание базы — только на своём локальном окружении.
