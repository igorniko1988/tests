# F2. Урок 1 — техники тест-дизайна

Задания: `practice/f2_01_techniques_answers.md` (пишешь ответы прямо в него).

## Зачем

Проверить «всё» невозможно: у поля суммы бесконечно много значений. Техники тест-дизайна
отвечают на вопрос **«какие проверки взять, чтобы их было мало, а баги находились»**.
На собесе их спрашивают всегда, и Senior должен применять их, а не только называть.

## 1. Классы эквивалентности

Делим все входные данные на группы, внутри которых система ведёт себя **одинаково**.
Из каждой группы берём **одно** значение.

Поле «сумма депозита» (amount > 0, не больше 18 знаков после запятой):

| Класс | Пример | Ожидание |
|---|---|---|
| положительное целое | `100` | ок |
| положительное дробное | `0.5` | ок |
| ноль | `0` | ошибка 422 |
| отрицательное | `-10` | ошибка 422 |
| не число | `"abc"` | ошибка 422 |
| пусто / нет поля | `""`, без amount | ошибка 422 |

Не нужно проверять 100, 200 и 300 — это один класс.

## 2. Граничные значения

Баги живут **на границах** (`>` вместо `>=`). Берём саму границу и соседей с двух сторон.

Пароль: длина от 8 до 128.

| Значение | Ожидание |
|---|---|
| 7 символов | ошибка |
| **8** | ок |
| 9 | ок |
| 127 | ок |
| **128** | ок |
| 129 | ошибка |

Классы эквивалентности + границы всегда идут вместе: сначала делим на классы, потом проверяем их края.

## 3. Таблица решений

Когда результат зависит от **комбинации условий**. Каждая колонка — правило (тест).

Размещение ордера BUY:

| Условие / правило | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| пользователь авторизован | нет | да | да | да |
| символ поддерживается | – | нет | да | да |
| хватает USDT (price × quantity) | – | – | нет | да |
| **результат** | 401 | 422 | 400 недостаточно средств | 201 создан |

`–` — неважно (дальше проверка не идёт). Таблица показывает, что ни одна комбинация не забыта.

## 4. Переходы состояний

Для объектов со **статусами**. Рисуем состояния и события, которые их меняют.

Ордер на нашей бирже:

```text
           частичное исполнение          полное исполнение
   NEW ─────────────────────▶ PARTIALLY_FILLED ─────────────▶ FILLED
    │                              │
    │ отмена                       │ отмена
    ▼                              ▼
 CANCELED ◀────────────────────────┘
```

Тесты:
- каждый **разрешённый** переход (NEW → CANCELED, NEW → FILLED, ...);
- **запрещённые** переходы — их часто забывают: отменить FILLED, отменить CANCELED повторно.

## 5. Pairwise (попарное тестирование)

Много параметров — комбинаций взрывается. 3 браузера × 3 ОС × 2 языка × 2 роли = 36 тестов.
Наблюдение: большинство багов вызывает **пара** параметров, а не все сразу.
Pairwise подбирает набор, где **каждая пара значений встречается хотя бы раз** — около 9–10 тестов вместо 36.
Инструменты: PICT, allpairspy (Python), онлайн-генераторы.

## 6. Другие техники (знать названия)

| Техника | Суть |
|---|---|
| **предугадывание ошибок** (error guessing) | по опыту: пробелы, юникод, очень длинное, SQL-инъекция, двойной клик |
| **исследовательское** (exploratory) | изучаем и тестируем одновременно, без готовых кейсов, с целью и таймбоксом |
| **use case / сценарии** | проверяем путь пользователя от начала до конца |

## 7. Пирамида тестов

```text
        /\        E2E / UI — мало, дорогие, медленные
       /  \
      /API \      интеграционные / API — основная масса у AQA
     /------\
    /  unit  \    юнит — много, быстрые (пишут разработчики)
```

Проверку лучше делать на **самом нижнем** уровне, где её можно сделать. Валидацию суммы — в API-тесте,
а не через UI. UI-тест — на то, что видит пользователь.

## Шпаргалка

| Ситуация | Техника |
|---|---|
| поле с диапазоном | классы эквивалентности + границы |
| несколько условий → разный результат | таблица решений |
| у объекта есть статусы | переходы состояний |
| много параметров-комбинаций | pairwise |
| нет документации | exploratory + error guessing |
