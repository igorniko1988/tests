# F2. Урок 2 — тест-кейсы, чек-листы, приоритизация, тест-план и стратегия

Задания: `practice/f2_02_test_docs_answers.md`.

## 1. Чек-лист и тест-кейс

**Чек-лист** — список того, что проверить, одной строкой на пункт. Быстро писать, удобно для опытной команды.

```text
[ ] Регистрация с валидными данными
[ ] Регистрация с занятым email → 409
[ ] Пароль 7 символов → 422
```

**Тест-кейс** — подробная проверка, которую выполнит любой человек одинаково.

| Поле | Пример |
|---|---|
| ID | TC-ORD-012 |
| Название | Размещение BUY-ордера при достаточном балансе |
| Предусловия | пользователь зарегистрирован, баланс USDT = 1000 |
| Шаги | 1. Войти. 2. Выбрать ETH-USDT, «Купить». 3. Цена 100, количество 2. 4. Нажать «Разместить» |
| Ожидаемый результат | ордер в таблице со статусом NEW; USDT available = 800, locked = 200 |
| Приоритет | High |
| Тестовые данные | email из фабрики, пароль `Secret123` |

Правила хорошего кейса:
- **одна цель** — одна проверка (не «проверить весь ордер»);
- **ожидаемый результат проверяемый**: не «работает корректно», а конкретные числа и статусы;
- **независимость**: кейс сам готовит свои данные в предусловиях.

Автотест — это тест-кейс в коде: предусловия → фикстуры, шаги → действия, ожидаемое → assert.

## 2. Приоритизация: risk-based

Всего не успеть — тестируем сначала то, где **риск** выше. Риск = **вероятность** бага × **ущерб** от него.

| Функция | Вероятность | Ущерб | Приоритет |
|---|---|---|---|
| списание баланса при ордере | средняя | **деньги** | P1 |
| логин | низкая | все заблокированы | P1 |
| сортировка таблицы ордеров | средняя | неудобно | P3 |
| цвет кнопки | низкая | почти нет | P4 |

Что повышает риск: деньги и данные, новая или переписанная фича, сложная логика, частые баги в прошлом,
то, чем пользуются чаще всего.

**Smoke** — минимальный набор «живо ли вообще» (логин, главный сценарий), запуск после каждого деплоя.
**Regression** — проверка, что старое не сломалось. **Sanity** — узкая проверка конкретного исправления.

## 3. Тест-план

Документ **на конкретный проект или релиз**: что, как, кто и когда тестирует.

| Раздел | Пример для биржи |
|---|---|
| объект и цели | релиз 1.2: стакан на WebSocket |
| в скоупе / вне скоупа | в скоупе: ордера, балансы, WS; вне: нагрузка |
| подход и виды тестирования | API-автотесты, UI e2e, ручное exploratory |
| окружения | stage :8081, данные — свежие пользователи на тест |
| критерии входа / выхода | вход: сборка на stage; выход: 0 открытых P1, 95% тестов зелёные |
| риски | WS нестабилен → отдельные тесты на reconnect |
| роли и сроки | кто, что, к какой дате |
| артефакты | отчёт Allure, список багов |

## 4. Тест-стратегия

Документ **на уровне компании или продукта**, долгоживущий: **как мы вообще тестируем**.
Тест-план отвечает «что делаем в этом релизе», стратегия — «по каким правилам всегда».

Что в стратегии: пирамида и соотношение уровней, инструменты (pytest, Playwright, Allure),
где запускаются тесты (CI на каждый PR, nightly regression), окружения и тестовые данные,
кто пишет какие тесты, метрики (flaky rate, время прогона, покрытие требований), definition of done.

На Senior-собесе часто просят: **«выстрой тестирование с нуля на проекте»** — это и есть рассказ стратегии.

## 5. Метрики качества (знать)

- **покрытие требований** — у скольких требований есть тесты;
- **flaky rate** — доля нестабильных тестов;
- **время прогона** и время от коммита до результата;
- **escaped defects** — сколько багов нашли пользователи, а не мы;
- **defect density** — багов на модуль/фичу (где копать сильнее).
