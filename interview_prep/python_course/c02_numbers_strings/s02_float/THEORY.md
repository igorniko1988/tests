# C2 · Раздел 2. float: почему 0.1 + 0.2 ≠ 0.3

[← раздел 1](../s01_int/THEORY.md) · [оглавление урока](../README.md) · [раздел 3 →](../s03_decimal/THEORY.md)

**Простыми словами.** `float` — число с плавающей точкой по стандарту IEEE 754 (64 бита). Он
хранит число в **двоичной** системе. Проблема в том, что многие «круглые» десятичные дроби в
двоичной системе **бесконечные** — как 1/3 в десятичной: 0,3333… Компьютер обрезает такую дробь,
и число хранится с крошечной ошибкой.

```
 1/3 в десятичной:   0,333333333…      — обрезали → неточно
 0.1 в двоичной:     0,000110011001100… — обрезали → неточно
```

```python
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False
```

Ни 0.1, ни 0.2, ни 0.3 не хранятся точно. Ошибки 0.1 и 0.2 сложились и стали видны.
Это **не баг Python** — так работает float в любом языке (JavaScript, Java, C).

---

### Как правильно сравнивать float

Никогда через `==`. Сравнивают **с допуском**: «числа отличаются меньше чем на очень маленькую величину».

```python
import math
math.isclose(0.1 + 0.2, 0.3)              # True — относительный допуск 1e-9
math.isclose(0.001, 0.002, abs_tol=0.01)  # True — абсолютный допуск

# в тестах:
import pytest
assert 0.1 + 0.2 == pytest.approx(0.3)
```

### Ошибка копится

```python
total = 0.0
for _ in range(10):
    total += 0.1
print(total)              # 0.9999999999999999
```

Каждое сложение добавляет свою крошечную ошибку. В расчётах с тысячами операций — например,
суммируя цены ордеров — копейки начинают «плыть».

### Округление: `round()` — банковское

`round(x)` округляет половину **к ближайшему чётному** (banker's rounding, ROUND_HALF_EVEN).
Это сделано специально: при округлении многих чисел ошибки вверх и вниз уравновешиваются.

```python
round(0.5), round(1.5), round(2.5), round(3.5)   # 0 2 2 4 — не 1 2 3 4!
round(-0.5)                                       # 0
```

Вторая ловушка — `round(x, 2)` с float:

```python
round(2.675, 2)    # 2.67, хотя «по-школьному» 2.68
```

Причина — снова двоичное представление: 2.675 на самом деле хранится как
`2.67499999999999982236431605997495353221893310546875`. Это меньше половины, и Python честно
округляет вниз. Вывод: **для денег float и round не годятся** — нужен Decimal (раздел 3).

### inf и nan

```python
print(1e308 * 10)          # inf — float переполняется в бесконечность (int — нет)
nan = float("nan")         # «не число», результат вроде inf - inf
print(nan == nan)          # False — NaN не равен ничему, даже себе
math.isnan(nan)            # True — единственный правильный способ проверки
```

Из-за NaN в данных сортировки и сравнения ведут себя странно — в тестах на ответы API с
числами стоит отдельно проверять, что нет `NaN` и `inf`.

---

**Частая ошибка.** `assert response["price"] == 0.3` после вычислений с float — тест то зелёный,
то красный в зависимости от порядка операций. Сравнивай через `pytest.approx` или переходи на
Decimal.

<details><summary>Проверь себя: что выведет?</summary>

```python
print(round(1.5) + round(2.5), 0.5 + 0.25 == 0.75)
```
`4 True`. `round(1.5) = 2`, `round(2.5) = 2` (к чётному). А 0.5 и 0.25 — степени двойки
(1/2 и 1/4), они хранятся в двоичной системе **точно**, поэтому сумма точная.
</details>
