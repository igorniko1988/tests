## Шпаргалка

1. Big-O — как растёт работа при росте входа n. Константы и младшие слагаемые отбрасываем, по умолчанию — худший случай.
2. Циклы подряд — складываем (O(n) + O(n) = O(n)), вложенные — перемножаем (O(n) × O(n) = O(n²)).
3. Внутренний цикл фиксированной длины — константа. Разные входы — разные буквы: O(n · m), O(n + m).
4. O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ). На миллионе: 1, 20, 10⁶, 2·10⁷, 10¹², ∞.
5. Логарифм — на каждом шаге отбрасываем долю данных (половину). Сортировка — O(n log n).
6. list: индекс, append, pop() — O(1); `in`, index, count, remove, insert(0), pop(0) — O(n).
7. dict/set: `in`, get, set, del — O(1) в среднем (O(n) в худшем); `in d.values()` — O(n).
8. Строки неизменяемы: `+=` в цикле — риск O(n²), собирай через `"".join`.
9. Сложность цикла = число повторов × цена тела. Ищи скрытый O(n) внутри цикла.
10. Память — то, что создала функция сама: коллекции, копии, срезы, стек рекурсии.
11. Обмен «память на время»: set/dict за O(n) памяти превращает O(n²) в O(n).
12. Размер входа подсказывает решение: ≤ 5 000 — можно n², 10⁵–10⁶ — нужно n или n log n.
13. Метод: уточнить → примеры → в лоб + сложность → улучшить → код → проверить руками. Всё — вслух.

## Собес

- **Что такое Big-O и зачем он нужен?**
  Это оценка того, как растёт время (или память) алгоритма при росте размера входа. Она не
  зависит от железа и мелочей реализации: константы и младшие члены отбрасываются, остаётся
  форма роста. Нужна, чтобы заранее понять, выдержит ли решение реальные объёмы данных, и
  сравнивать решения между собой.

- **Какая сложность у `x in list` и `x in set`? Почему?**
  У списка O(n): он не знает, где лежит значение, и сравнивает с каждым элементом по очереди.
  У множества O(1) в среднем: это хеш-таблица, по `hash(x)` сразу вычисляется ячейка. В худшем
  случае, при массовых коллизиях хешей, — O(n), но со встроенными типами это практически не
  встречается. Поэтому для частых проверок «есть ли» данные кладут в set.

- **Что значит «append работает за амортизированное O(1)»?**
  Список выделяет память с запасом. Пока запас есть, append просто кладёт ссылку в свободную
  ячейку — O(1). Когда место кончилось, выделяется блок побольше и все элементы копируются —
  O(n), но это случается всё реже по мере роста. Если сложить стоимость n добавлений и
  разделить на n, получится константа — это и есть амортизированная оценка.

- **Почему вложенный цикл — это O(n²)? Всегда ли?**
  Для каждого из n шагов внешнего цикла внутренний делает свои n шагов — итого n · n. Но не
  всегда: если внутренний цикл фиксированной длины (`range(3)`), это O(n); если по другому
  входу — O(n · m); в технике двух указателей вложенный `while` в сумме двигает указатель не
  больше n раз, и всё вместе O(n). Считать надо общее число шагов, а не уровни вложенности.

- **Как по размеру входа понять, какое решение ждут?**
  Python делает около 10⁷ простых операций в секунду. Подставляю максимальный n в сложность:
  при n до нескольких тысяч O(n²) укладывается, при 10⁵–10⁶ нужно O(n) или O(n log n), при
  n ≤ 20 допустим перебор O(2ⁿ). Если ограничений нет в условии — спрашиваю у интервьюера.

- **Что такое сложность по памяти? Сколько памяти у рекурсии?**
  Объём дополнительных данных, которые создаёт решение, в зависимости от n: новые коллекции,
  копии, срезы. Рекурсия глубины n занимает O(n) памяти на стек вызовов, даже без коллекций.
  В Python глубина по умолчанию ограничена ~1000 вызовами.

- **Чем отличаются лучший, средний и худший случай?**
  Это оценки для разных входов одного размера. Поиск в списке: лучший — элемент первый, O(1);
  худший — его нет, O(n); средний — около n/2, тоже O(n). По умолчанию говорят про худший
  случай, для хеш-таблиц — про средний, оговаривая худший.

- **Какая сложность у `sorted()`? А у `list.sort()`?**
  Обе O(n log n) по времени (Timsort). `sorted` возвращает новый список — O(n) памяти;
  `list.sort` сортирует на месте и возвращает None. На почти отсортированных данных Timsort
  работает быстрее, вплоть до O(n).

- **Как ты подходишь к задаче на лайвкодинге?**
  Уточняю условие и краевые случаи, разбираю примеры, называю решение в лоб и его сложность,
  ищу, что в нём повторяется, и улучшаю (чаще всего через dict/set, сортировку или указатели),
  называю новую сложность, пишу код с понятными именами, прохожу его руками на примере и
  краевых случаях. Всё проговариваю вслух.
