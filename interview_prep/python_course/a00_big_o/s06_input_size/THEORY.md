# A0 · Раздел 6. Размер входа подсказывает решение

[← раздел 5](../s05_memory/THEORY.md) · [оглавление урока](../README.md) · [раздел 7 →](../s07_method/THEORY.md)

**Простыми словами.** В условии задачи часто написано: «`1 ≤ len(nums) ≤ 10⁵`». Это не
формальность, а **подсказка**: по ней видно, какая сложность от тебя нужна. Если в условии
ограничений нет — **спроси**: «Какого размера могут быть данные?» Интервьюеры это ценят.

Логика простая. Python делает около **10⁷ простых операций в секунду**, решение должно
укладываться примерно в секунду. Подставляем n в формулу сложности и смотрим, влезает ли:

| Максимальный n | Влезает по времени | Что обычно ждут |
|---|---|---|
| ≤ 10–20 | O(2ⁿ), O(n!) | полный перебор, backtracking (A9) |
| ≤ 500 | O(n³) | три вложенных цикла — ещё нормально |
| ≤ 5 000 | O(n²) | вложенный цикл допустим |
| ≤ 10⁵ – 10⁶ | O(n log n), O(n) | сортировка, dict/set, два указателя, окно |
| ≥ 10⁸ или «поток данных» | O(log n), O(1) на запрос | бинарный поиск, формула, предподсчёт |

**Пример рассуждения вслух:** «n до 10⁵. Решение в лоб — два вложенных цикла, это 10¹⁰
операций, не уложится. Нужно O(n) или O(n log n). Раз я ищу пару, попробую dict».

---

### Сколько это в реальности

```python
import time

def quadratic(n):
    count = 0
    for i in range(n):
        for j in range(n):
            count += 1
    return count

start = time.perf_counter()
quadratic(3_000)                       # 9 млн шагов
print(time.perf_counter() - start)     # ≈ 0,3–0,5 с на обычном ноутбуке
```

```
 n = 3 000   → n² = 9 · 10⁶      ≈ 0,4 с
 n = 30 000  → n² = 9 · 10⁸      ≈ 40 с     ← данных в 10 раз больше, времени в 100
 n = 300 000 → n² = 9 · 10¹⁰     ≈ час
```

Это и есть главный аргумент Big-O: решение, которое «быстро работает на моём примере из 5
элементов», может умереть на настоящих данных.

### А что в работе AQA

Эта же логика нужна не только на собесе:

- **Сравнение двух выгрузок** (ответ API против базы, 100 000 записей): «для каждой записи
  поискать в другом списке» — O(n²), минуты. Через dict по id — O(n), доли секунды.
- **Поиск дублей в логах** на миллион строк — только через set/Counter.
- **Тест на производительность** часто ловит именно случайный O(n²) в коде сервиса: на 100
  записях всё быстро, на 10 000 — таймаут.

---

**Частая ошибка.** Сразу писать «оптимальное» решение, не сказав ни слова. Сильнее: назвать
решение в лоб и его сложность, сравнить с ограничением на n и **объяснить**, почему нужно
лучшее. Так интервьюер видит ход мысли — а это половина оценки.

<details><summary>Проверь себя: какое решение ждут?</summary>

1. `len(s) ≤ 10⁵`, найти первый уникальный символ — O(n): Counter + проход.
2. `n ≤ 15`, найти все подмножества с суммой k — перебор 2¹⁵ ≈ 32 000 вариантов, O(2ⁿ) — нормально.
3. Отсортированный массив из 10⁹ элементов, найти число — O(log n), бинарный поиск.
4. `n ≤ 1000`, найти пару с суммой k — подойдёт и O(n²) (10⁶ операций), но O(n) через dict лучше и стоит его назвать.
</details>
